# API Docs — 接口文档自动生成(对标 project-archive 的活文档模式)

> **随包说明**:本技能随 `dsh-dev-workflow` 一起发布(包内 `skills/api-docs/`),
> 只在**已激活**的 dev-workflow 项目里出现在 DSH 技能目录中。用 `skill` 工具加载它时给出的
> "Base directory for this skill" 就是它的根目录,文中的相对路径(`references/`、`scripts/`、
> `templates/`、`assets/`)都相对那里解析。
>
> **工具名对照**(本文或许带着别的工具链的写法,在 DSH 里对应的是):`Read`/`read_file` → `read`,
> `Write`/`write_file` → `write`,`Edit` → `edit`,`Bash`/`terminal` → `pwsh`,
> `Glob`/`Grep`/`search_files` → `glob`/`grep`,`TodoWrite` → `todo_write`,
> `Task`/`delegate_task` → `subagent`,`web_extract` → `web_fetch`。
> 文中提到的脚本与模板**只有随包时才存在** —— 加载后先照 Base directory 核一眼,没有的步骤跳过,
> 或按文中原则自行实现,不要到别处去找。

把 Spring Boot 项目的 Controller/Service 变成结构化 `接口文档.md`,供特工开发/联调/测试时读取。**能自动扫描的绝不问用户**,接口语义从代码注释 + 方法签名 + 上下文推断,扫不到的才问。

## 触发词

- 「给 X 生成接口文档」「接口文档」「看下有哪些接口」「生成 API 文档」
- dev-workflow 开工时自动检查:有接口文档 → 读取;没有 → 生成(Controller 层存在时)

## 新项目 vs 老项目(⭐ 先判断项目阶段)

| 阶段 | 判定 | 动作 |
|---|---|---|
| **老项目**(已有 Controller) | `find src -name "*Controller.java"` 有结果 | 走下方「扫描全量」流程 |
| **新项目**(Controller 为空) | 没有 Controller 或项目刚初始化 | 走下方「计划接口清单」流程 |

### 新项目 · 计划接口清单(开发契约)

**场景**:代码还没写(或刚开始),没有 Controller 可扫。此时不生成空文档,而是用**需求清单/架构师 API 契约**预生成「计划接口清单」:

```markdown
# 接口文档:<项目名>(计划版)

> 状态:计划接口清单(2026-08 生成,基于需求清单/架构契约)
> 开发完成后用 `--update` 重扫转正式版

## 计划接口概览
| # | 方法 | 路径(规划) | 接口名 | 说明 | 状态 |
|---|------|------------|--------|------|------|
| 1 | POST | /api/v1/xxx | xxx | (来自需求) | 📋 待实现 |

## 计划接口详情

### 1. POST /api/v1/xxx
- **接口名**:xxx
- **功能说明**:(来自需求清单/架构契约)
- **入参**:(规划:字段/类型/说明)
- **出参**:(规划)
- **来源**:需求 R1 / 架构契约 §3.2

## 待确认
- (规划接口的歧义点,≤3 问)
```

**输入来源(按优先级)**:① 架构师 API 契约(有则直接用)② 需求清单(项目经理产出)③ 用户口头描述(问 ≤3 个关键问题补全)。

**落盘**:项目根 `接口文档.md`,开头标注「计划版」。**用途**:作为开发契约——前端 mock 按它写、后端实现按它做、联调按它核对(衔接 ③.5 联调关卡)。

**转正**:开发完成、Controller 实际存在后,`--update` 重扫:计划接口与实现一致的标记 ✅ 已实现;不一致的标注差异(以实际实现为准);新增的补上。计划版标注移除,转正式版。

### 老项目 · 扫描全量(现有流程)

## 流程:扫描 → 填模板 → 只问缺失 → 确认落盘

### Step 1 · 自动扫描(不提问)

**扫描 `src/main/java` 下的接口代码**(Java/Spring Boot 项目;非 Java 项目跳到 Step 3 问):

1. **Controller 层**(`*Controller.java`):
   - 类注解:`@RestController` / `@Controller` / `@RequestMapping("/xxx")` → 基础路径
   - 方法注解:`@GetMapping` / `@PostMapping` / `@PutMapping` / `@DeleteMapping` / `@PatchMapping` / `@RequestMapping` → 完整路径 + HTTP 方法
   - 方法签名:参数(含 `@RequestBody` / `@RequestParam` / `@PathVariable` / `@RequestHeader`)、返回类型
   - 代码注释(类注释/Javadoc/行内注释)→ 接口用途

2. **Service 层**(`*Service*.java`,可选):
   - 接口方法签名 + 注释 → 补全业务语义(Controller 薄,业务在 Service)

3. **DTO/入参出参**(可选):
   - `@RequestBody` 引用的 DTO 类字段 → 入参结构

**提取方法**:用 `grep/glob` 找 `*Controller.java`,`grep` 抓注解行,`read` 读关键文件(类头注释 + 方法注释)。

### Step 2 · 填模板生成草稿

```markdown
# 接口文档:<项目名>

## 接口概览
| # | 方法 | 路径 | 接口名 | 说明 | 状态 |
|---|------|------|--------|------|------|
| 1 | POST | /cicd_agent/xxx | xxx | xxx | ✅ 已实现 |

## 详细接口

### 1. POST /cicd_agent/xxx
- **接口名**:xxx
- **功能说明**:(来自代码注释/签名推断)
- **入参**:
  - header:xxx
  - query/param:xxx
  - body(DTO):字段名/类型/说明
- **出参**:xxx
- **异常**:xxx(如有 @ExceptionHandler/业务异常)
- **权限**:xxx(如有鉴权注解/JWT 校验)
- **源码位置**:src/main/java/com/.../XxxController.java:行号

## 未实现/待确认
- (扫描到 TODO/未映射的路径,或语义不明的接口)
```

### Step 3 · 只问缺失项(≤3 个问题)

**只问代码里推不出来的**:
1. 有没有接口是**内部调用**不用写文档的?(过滤清单)
2. 接口的**业务语义**明显有歧义的(注释缺失且签名看不出用途)——挑关键的 1-2 个问,别每个都问
3. 文档要给谁看?(开发联调用 / 测试用 / 交付客户用 → 影响详略)

**规则**:注释和签名能推断的**不重复问**;语义不明的接口先写「推断:xxx」标注,用户没意见就保留。

### Step 4 · 确认落盘

- 保存位置:项目根目录 `接口文档.md`(优先),与项目档案并列;或 `docs/接口文档.md`
- 展示概览表 + 关键接口示例,用户确认后落盘
- **自动记忆/增量更新**:项目接口变化时(新增 Controller/方法/路径),用 `--update` 模式重新扫描,只补新增/变更的接口,保留已确认的语义描述

## 自动记忆机制(对标 project-archive)

接口文档也是**活文档**——执行中学到的信息自动沉淀:

### 触发时机 1:用户纠正(最高优先级)
- 用户说「这个接口其实是查列表不是详情」「路径改成了 /v2/xxx」→ **立即** patch 对应接口条目

### 触发时机 2:开发/测试中发现新接口
- 特工执行中发现新增的 Controller/方法/路径 → 记入「待补接口」清单,角色结束时统一追加

### 触发时机 3:接口变更
- dev-workflow 角色完成后,重新扫描对比,差异自动更新(新增的补上,删除的标「已下线」不直接删)

### 防失控规则
1. **只更新事实类**(路径/方法/入参/出参/状态);**业务语义确认类改动问用户**
2. 更新前备份(`接口文档.md.bak`)+ 展示 diff
3. **批量更新**:攒到角色结束统一写,不逐条打扰
4. 已确认的语义描述(用户改过的)在重扫时**保留**,不覆盖用户的人工修正——重扫只动结构变化

### 自动记忆执行检查
- [ ] 只改了接口事实?没覆盖用户人工修正的语义?
- [ ] 没写密码/密钥/内网敏感地址?
- [ ] 备份 + diff 了?
- [ ] 批量写入而非逐条打扰?

## 与 dev-workflow / project-archive 衔接

- **开工**:dev-workflow 检查项目档案+ `接口文档.md`(本技能)——两个都在,特工开工就有「项目背景 + 接口全貌」
- **档案联动**:接口文档生成后,在项目档案的「目录结构」里补一行 `接口文档.md 见 api-docs`;接口文档里发现的框架/依赖新事实,回写项目档案

## Pitfalls

- **只扫 Java/Spring**:非 Java 项目(如纯前端/脚本)直接跳过扫描,问用户是否需要手写接口清单
- **路径拼接**:类级 `@RequestMapping` + 方法级映射要正确拼接,别漏类级前缀
- **GET 查询参数**:`@RequestParam` 的 query 参数要列全,别只记 body
- **RESTful 风格项目**:方法名可能不直观,以注解路径为准,不要用方法名猜路径
- **大项目**:Controller 超过 20 个时,先问用户「全部生成还是只生成核心模块」,别一口气扫完烧 token
- **不写敏感信息**:接口文档不记录密码、token、内网完整地址(脱敏为主机名)
